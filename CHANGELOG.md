## [0.19.0] - 2026-11-22

### Upgrading

Migration `org.0020_leadership` adds a `track` column to the contribution ledger (`org_contributionentry`) and creates the leadership tables. On SQLite adding the column rebuilds the whole ledger table under a write lock; it is quick at current row counts, but deploy with `just dev::release` in a quiet window. Existing rows read `track="contribution"`, so no points change.

The new Leadership feature is locked for every organization until a site admin unlocks it. While it is locked, completing an event records nothing for leadership. Each organization starts with the default settings, the default point values and the four default traits (Communication, Drafting, Composure, Sportsmanship); nothing needs to be configured before unlocking.

### Added

- Organization Leadership (locked feature): captains earn points for captaining, placing and finishing the draft, and teammates rate them 1 to 5 on per-org traits during a review window after the event. Ratings stay hidden until the window closes with enough reviews, raters can see their own past reviews, and org admins can moderate reviews of anyone but themselves. Leadership boards (overall rating, per-trait rating and points) are served by the standing endpoints. Backend and API only; the screens ship in a later release.

### Changed

- `just dev::release` now pulls the release images first and stops if the pull fails,
  before it touches the database or the running stack. It then runs
  `makemigrations --check` and stops, with the site still up, if the models have changes
  with no migration. Only then does it stop the release stack, run migrations and start
  the new version, so a release that drops a column no longer
  needs a manual stop-first sequence. The site is down for the migration and container
  start (seconds). It pulls the exact `:VERSION` images the release stack runs instead of
  calling `docker::release::pull`.
- CI: a `prepare` job in the Playwright workflow builds each missing stack image and the
  test DB once and pushes it under its content-hash tag only, so the test jobs pull
  instead of each rebuilding. PR builds never push `:latest` or the registry build cache
  (`docker::buildx --hash-only`, `docker::db::push --hash-only`).
- The "Confirm attendance via Discord" event setting is now "Post attendance reminder in Discord", and its description says what it does: post a reminder in the announcement channel before the event. It never tracked replies; use the ready check to require confirmation.
- The ready check settings now say who gets each message: members by DM for the Ready
  request, nudge, sign-up and drop notices, and org or league staff, the event host and
  helpers through ops notices for the per-member chase and held or non-binding checks.
  Both ready check blocks also say they are not active yet.

### Fixed

- The event signup form scrolls again when it is taller than the window, so the rank
  fields below the fold can be filled in and Sign Up enables (#799). Other scrollable
  panels built on the same scroll area now size the same way.
- An event's Tournament Info card shows "No limit × 5" instead of "null × 5" when the
  team count is unlimited.
- The event picker on manual contribution awards shows each event's date, so
  repeating events with the same name can be told apart.
- Captain's Mode Draft Time accepts only positive whole seconds: typing `0` now sets 1
  second, like any value below 1, instead of jumping to the 10-second default. An empty
  field still falls back to 10.

## [0.18.0] - 2026-11-22

### Upgrading

The `app` and `events` migrations up to 0.17.0 are squashed and the replaced files are
deleted. A database at 0.17.0 or later needs nothing: `migrate` records the squashed
migrations as applied without running them. A database older than 0.17.0 cannot
migrate on this release; upgrade it to 0.17.0 first, then to this release.

Migration `org.0018` drops the `OrgUser.mmr` column. Org MMR has been stored one row
per game since 0.17.0, whose `org.0015` and `org.0016` copied every non-zero
`OrgUser.mmr` to the Dota 2 org MMR and kept the column in sync; nothing is copied
in this release.

This release must be deployed stop-first. `just dev::release` migrates before it pulls
images and recreates containers, and the old containers fail on every org member query
once the column is gone. From the repo root on the release host, after `git pull`:

```bash
just docker::release::pull
scripts/in-env.sh release . .venv/bin/python -m scripts.slots --root . compose --stack release down
just dev::release
```

The site is down from the second command until the third finishes (seconds of
migration plus container start).

During the deploy, a browser still running the old page gets a 400 "mmr requires
mmr_game_type; reload the page" when it saves an org MMR. Reloading the page fixes it.

Rollback (per-game org MMR rows, including Deadlock, are kept; `OrgUser.mmr` is
refilled from the Dota 2 values):

1. Stop the release stack:
   `scripts/in-env.sh release . .venv/bin/python -m scripts.slots --root . compose --stack release down`
2. From this release's checkout (migrations run from the host), run
   `just db::manage release migrate org 0017_retarget_default_league_to_league`.
3. Remove the old version's cached keys so the old image cannot serve pre-upgrade
   member data. Start only Redis and delete the keys, replacing `0.17.0` with the
   version you are going back to:
   `scripts/in-env.sh release . .venv/bin/python -m scripts.slots --root . compose --stack release up -d redis`, then
   `scripts/in-env.sh release . .venv/bin/python -m scripts.slots --root . compose --stack release exec -T redis sh -c "redis-cli --scan --pattern 'dtx-v0.17.0:*' | xargs -r redis-cli unlink"`.
   Alternatively, start the old version with a new `DEPLOY_VERSION` in
   `docker/.env.release` so it reads an empty cache prefix.
4. Check out the old version and run `just dev::release`.

Run migrations. `app.0113_widen_steam_account_id` widens the user Friend ID column to
hold every Steam account ID. `app.0114_copy_profile_friend_ids` copies the Friend ID
from each player's Dota 2 and Deadlock profiles onto their account when the account
has none yet. A player whose profiles hold different IDs, or whose ID another account
already holds, is skipped and logged as `steam_friend_id_backfill_skipped` with the
user id and reason (`ambiguous` or `taken`); set those by hand in the admin.
`org.0019_remove_unverified_friend_id` then drops the profile Friend ID column, so
take a database backup first if you want to keep the skipped values. Reversing 0114
is a no-op; reversing 0019 restores an empty column.

### Security

- Event signups no longer leak a member's org MMR to viewers outside the organization's
  member rule through `suggested_mmr`; for those viewers the suggestion is never derived
  from the org MMR.
- Creating a team now needs edit access to its tournament. Any logged-in user could
  create a team in any tournament through `POST /api/teams/`, while
  `POST /api/team/register` refused org and league staff (#739).
  The tournament Teams tab now offers team creation to the same people.

### Added

- Image builds now print their slowest BuildKit steps and cached-step count, and add them to the job summary, so you can see which layer dominates a build.
- `just ci::timing` pulls queue waits, step timings, per-command timings (including inside composite actions) and those layer reports for recent CI runs into `.ci-timing/summary.md`.
- Event staff see a turnout forecast on upcoming events of organizations with Conduct:
  how many signed up, how many are expected to show, and how many await approval.
- Event staff record attendance on the event page from roll call onwards: select
  members and mark them attended, no-show, late cancel or excused with one audited
  reason. Org staff can also add org members who played without signing up as
  walk-ins.
- Signup rows on the event page and on roll call show each member's show rate (or New)
  to event staff, and whether Conduct would hold the member for approval or block them.
- Org MMR per game: every organization member now has a separate Dota 2 and Deadlock
  org MMR. Both can be viewed and edited on the organization Users tab, the user card and
  the player modal (hotkeys R for Dota 2, K for Deadlock). Adding another game later
  needs no new column or table.
- Deadlock tournaments balance teams, order shuffle drafts, total team MMR and pick a new
  captain by Deadlock org MMR. Dota 2 tournaments behave as before.
- The organization CSV import has a Game select that picks which game's org MMR the
  `mmr` column sets; the tournament import uses the tournament's game.
- Approving a Deadlock signup shows the player's self-reported Deadlock rank and its
  date, and writes the Deadlock org MMR.
- New docs page: Org MMR per game.
- Hero draft: heroes suggested by your team show the suggesters' avatars on the
  grid (green, top-left for picks; red, bottom-right for bans, shown only during a
  ban round), and on your turn the heroes suggested for the current action are
  highlighted. Right-click a hero you suggested to remove your suggestion.

### Changed

- CI Playwright jobs run the tests inside a new `playwright-runner` image (`frontend/Dockerfile.playwright`: the official Playwright image for the pinned `@playwright/test` version plus `npm ci`), so they keep Playwright's bundled headless Chromium shell, and Playwright and backend test jobs no longer install Python, Poetry, Node or Playwright browsers on the runner. `just docker::all-push` builds and pushes the runner; `just docker::all-pull` pulls it when `DF_PW_CONTAINER=1`.
- CI test jobs pull the stack images and test database in the background while Python, Node and Playwright are set up, and no longer boot a buildx builder unless an image has to be rebuilt.
- Draft-started DMs now open the Discord Activity in one click when the draft has a known voice channel: the channel already assigned to the draft, or, for team drafts, the event's voice channel. The **Launch / Join Activity** button links straight to an invite for that channel. Drafts without a known channel keep the current two-step launch from your own voice channel.
- API: member payloads carry `mmr_game_type`, the game their `mmr` was resolved for. In
  Deadlock tournaments and events `mmr` is now the Deadlock org MMR. The org users
  endpoint, the org user PATCH response and claim requests add the full per-game set
  (`game_mmrs`, `target_game_mmrs`); gated event signups add `org_user_game_mmrs`,
  `self_reported_rank` and `self_reported_rank_date`.
- API: `PATCH /api/organizations/{id}/users/{org_user_id}/` takes
  `{"game_mmrs": {"<game_type>": int | null}}`. Values must be integers in 0–20000 and
  keys known game ids, or the request returns 400. `null` or 0 clears a game. A bare
  `{"mmr": n}` without `mmr_game_type` returns 400. Each changed game logs an `OrgLog`
  `set_mmr` entry.
- Signup approval writes the org MMR of the event's game. The Dota verification flags
  are set only for Dota events. `suggested_mmr` and `suggested_mmr_range` can be `null`
  (source `"none"`) for games without a suggestion.
- The MMR approval dialog now requires a value; Deadlock needs at least 1.
- CSV import rejects `mmr` cells outside 0–20000 as row errors instead of storing them,
  and the tournament import refuses the `league` MMR target for non-Dota tournaments.
- The Django admin shows org MMRs read-only; edit them from the organization page.
- Deadlock tournaments no longer show the league MMR on player cards and player strips;
  league MMR is a Dota 2 value and still shows in Dota 2 tournaments.
- The event signup form and the org Dota 2 profile card show your Friend ID
  read-only once it is set, with a note to contact an admin to change it, and only
  ask for it while it is empty (#717).
- Each player now has one Steam Friend ID, kept on their account instead of on each
  organization's Dota 2 and Deadlock profile. Web and Discord signups fill it in when
  it is empty and never replace it: a signup with a different Friend ID is refused
  with "Your Friend ID is already set to X; contact an admin to change it". Friend
  IDs above 2147483647 are now accepted (#717).
- Event, series and event-defaults dialogs respond faster: ticking a checkbox or
  changing a setting now redraws only that field, not every tab of the dialog.
- League backend code moved from `app` into the `league` Django app, ahead
  of the model move. The league permission helpers and `IsLeagueAdmin` are
  now in `league.permissions`; tournament, game and lobby checks stay in
  `app.permissions_tournament`. `LeagueView` is now in `league.views`,
  `LeagueSerializer` in `league.serializers`, the league SSR view in
  `league.ssr`, the league admin/staff/member endpoints in
  `league.views_admin_team`, and the rating and match finalization services
  in `league.services`. The unused `IsLeagueStaff` permission class is
  removed.
- The `view` field of `drf_error_response` logs for these endpoints now
  reads `league.views.LeagueView`, `league.views_admin_team.*` and
  `league.ssr.*` instead of `app.views_main.*`, `app.views.admin_team.*` and
  `app.views.ssr.*`. Log queries that filter on it need updating.
- League HTTP paths, URL names, payloads and models are unchanged.
- The `League`, `LeagueRating`, `LeagueMatch`, `LeagueMatchParticipant` and
  `LeagueLog` models moved from `app` into the `league` Django app. The
  migrations are state-only: the tables keep their `app_league*` names
  (including `app_league_admins` and `app_league_staff`) and no schema
  changes on deploy.
- The five ContentType rows are relabelled from `app` to `league`, so the
  permission labels change from `app.*_league*` to `league.*_league*`.
  Existing user and group grants carry over.
- The cacheops profile key `app.league` is renamed to `league.league`, with
  the same profile.
- No admin URL changes, since none of the five models is registered in
  admin. No logger name, HTTP or WebSocket path, payload or
  `_meta.label`-derived key changes either.

### Removed

- API: the event signup endpoint no longer accepts `profile.unverified_friend_id`, and
  the org Dota 2 profile endpoints read and write `steam_account_id` (the player's
  Friend ID, a number) instead of `unverified_friend_id` (#717).

## [0.16.0] - 2026-11-21

### Upgrading

Run migrations: `events.0032` adds `eligibility_reasons` and
`eligibility_checked_at` to event signups. Existing signups start with no stored
reasons; they fill in the next time the player's profile changes or staff
re-check the signup.

Org conduct adds three migrations: `org.0013_conduct` (the attendance outcome and conduct
settings tables), `events.0034_event_conduct_finalized_at` (a nullable field on events)
and `app.0110_orglog_conduct_actions` (new org log action choices). They run with the
usual migrate step and need no data backfill: past events have no attendance record, so
tracking starts with the next event that closes after an organization gets the feature.
Reversing the migrations drops the new tables and the `conduct_finalized_at` field.

The feature is locked by default and every enforcement mode is off, so nothing changes
for members until a site admin unlocks it and an organization admin turns a mode on.

### Security

- Removed the unused `/ajax-auth/<backend>/` login endpoint, which crashed on every
  request. Discord login is unaffected.
- The hourly limit on the public avatar refresh at `/api/avatars/refresh/` now claims
  its slot atomically, so simultaneous page loads can no longer queue the refresh twice.

### Added

- Signups held for approval now record why: each unmet event requirement is
  stored as a reason with a code, a message, the rule it enforces and, where the
  player can fix it, a link to their profile. Event staff and the player see the
  reasons on the signup; other members do not (#500).
- Staff can re-check a signup's requirements with
  `POST /api/events/signups/<id>/recheck/`, and players can ask
  `GET /api/events/<id>/eligibility/?intent=main|maybe` what they are missing
  without joining the organization (#500).
- Refused web signups now return `reasons` alongside `error` (#500).
- Events can mention their signed-up members on Discord a set number of minutes
  (5, 10, 15, 30 or 60) before start, as replies to the signup post (#540). The
  option is off by default; organizers choose the main list only or all active
  signups. Members are mentioned in chunks of 80 per message, and staff can fire
  the mention by hand from the event's task schedule.
- Teams: staff and system changes to a tournament team's leadership and roster are now
  recorded in a read-only team audit log (Django admin: Team logs), with who made it,
  from where, the reason and the roster before and after. This covers the team
  management service, the existing team edit (PATCH), and captain successions, kept
  empty teams and team deletions done by the system; it does not cover team creation,
  draft resets or plain member removals done by the system. A team service backs the
  upcoming staff team management tools: change captain or deputy, mark a dropout,
  restore a member, add, remove or sub in a stand-in, and rename, with a reason required
  when acting on another player and a staff override for the stand-in limit and
  eligibility (#544).
- Team drafts: the event feed shows when a team's captain changes mid-draft (#544).
- Team drafts: stand-ins and dropouts can no longer be drafted, undoing a pick refuses
  when the picked player has since been made captain, and rebuilding teams from the
  draft picks refuses once staff have changed a team (#544).
- Teams: staff can change team captains, deputies, stand-ins and dropouts, rename teams and read a team's change history through new API endpoints, each change requiring a reason (#545).
- Teams: team and tournament API responses now list captain or deputy problems for each team (#545).
- Teams: staff can manage a tournament team's captain, deputy, stand-ins and dropouts from the team modal, with a reason for every change and a change history (#546).
- Teams: staff see which teams have a captain or deputy who is not a member, or a deputy who is also the captain, on the Teams tab, team cards and team modal, and can fix them from the management dialog (#546).
- Shared staff override contract: one policy check that follows the organization's
  staff override setting, one `409 override_required` response, a reason requirement,
  and a warning dialog that lists each broken rule and asks for a reason. Endpoints
  adopt it in follow-up changes (#585).
- HeroDraft: press Enter anywhere in the draft to open chat and start typing. An Enter
  keycap on the empty chat box shows the shortcut; Escape closes chat again.
- Organizations can track attendance for their events. When an event completes, every
  expected member is recorded as attended unless staff mark them as a no-show, late
  cancel or excused. Staff edits need a reason and are written to the org log.
- Each member gets a show rate built from recent attendance, with older events counting
  less, available through the new conduct and organization standing endpoints.
- Organizations can opt in to enforcement for members below a threshold: send them to
  the back of the line, require approval for their signups, or block self sign-up.
  Organizers can still add or approve them; a blocked member added by staff waits for
  approval.
- The feature is locked by default and a site admin unlocks it per organization.
- New organization standing endpoints list the tracks a viewer can see and serve any
  track's leaderboard, including contributions ranked by number of entries.
- Test and demo data: the real test users now show their Discord avatars. Populate applies avatar hashes committed in `backend/tests/data/discord_avatars.py`, so it needs no Discord token; `just db::avatars::refresh` refetches them.
- Hero Draft: team chat, all chat (/all) and right-click hero pick/ban suggestions visible only to your team, with a click-through preview of your team's new messages while the chat is closed.
- The frontend design-system lint now catches colour literals inside Tailwind arbitrary values (`shadow-[...rgba(...)]`, `text-[#5865F2]`) with `draftforge/no-arbitrary-color-literals`; pure black and white shadows stay allowed. The 14 existing cases use theme tokens instead: hero draft pick/ban/turn glows, the team draft reserve tint (`error`), Discord accents (`discord`), the navbar label (`primary`), the node loading ring (`info`) and the brand select glow.

New optional environment variables, all safe to leave unset. `REDIS_KEY_SCOPE` prefixes raw Redis keys (draft tick, Discord rate limit, activity intents and the signup post lock) for deployments that share one Redis; it defaults to empty, so existing keys keep their names. `SIGNUP_POST_DEBOUNCE_SECONDS` (default 2) and `SIGNUP_POST_LOCK_SECONDS` (default 90) set how long a Discord signup post edit waits before running and how long one edit may hold the per-event lock. `SIGNUP_POST_READ_RETRIES` (default 3) sets how many times an edit is retried when the signup list cannot be read before it is skipped. `SIGNUP_POST_RETRY_SECONDS` (default 2, at least 1) sets the wait before each of those retries and before an edit tries a held lock again. `SIGNUP_POST_BUSY_WARN_PASSES` (default 5) sets how many held-lock passes an edit makes before it logs one `signup_update_lock_stalled` warning; each pass is logged as `signup_update_lock_busy` at debug, and a skipped edit's `signup_list_unavailable` warning carries `retries_exhausted=true`. `SIGNUP_POST_DISABLED=true` turns the debounce and lock off (`DISABLE_CACHE` does too).
